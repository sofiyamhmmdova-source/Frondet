01 · Nəzəri hissə

Əvvəlcə anlayaq, sonra yazaq

Kodu yazmazdan əvvəl altı əsas anlayışı aydınlaşdırırıq. Bunlar React-də API ilə işləyən demək olar ki, hər komponentin əsasını təşkil edir.

01 / 06

REST API əsasları

REST (Representational State Transfer) — server ilə client arasında HTTP protokolu üzərindən məlumat mübadiləsi üçün istifadə olunan arxitektura üslubudur. Hər resurs özünəməxsus ünvana (endpoint) malikdir və bu ünvana müxtəlif HTTP metodları ilə müraciət olunur.

  • GET — məlumat almaq
  • POST — yeni məlumat yaratmaq
  • PUT / PATCH — məlumatı yeniləmək
  • DELETE — məlumatı silmək

Cavab adətən JSON formatında qaytarılır və status kodu ilə müşayiət olunur (200, 404, 500 və s.).

02 / 06

Fetch API vs Axios

Hər ikisi HTTP sorğusu göndərmək üçündür, amma davranışları fərqlidir. Fetch brauzerə daxili gəlir, Axios isə ayrıca kitabxanadır və bir sıra əlverişli funksiyaları özündə birləşdirir.

  • Fetch — manual JSON çevrilməsi (response.json())
  • Axios — cavabı avtomatik JSON-a çevirir
  • Axios — 4xx/5xx statuslarını avtomatik xəta kimi tanıyır
  • Fetch — response.ok-u özün yoxlamalısan
03 / 06

useEffect daxilində data fetching

Sorğu birbaşa komponentin gövdəsində deyil, useEffect daxilində göndərilməlidir. Əks halda hər render zamanı yeni sorğu gedər və sonsuz dövr yarana bilər.

  • Asılılıq massivini ([]) düzgün təyin et
  • Sorğunu ayrıca async funksiyaya çıxar
  • Lazım gələrsə cleanup funksiyası qaytar
04 / 06

Loading / error / success idarəetməsi

Hər sorğunun üç mümkün nəticəsi var: gözləmə, uğur, xəta. Bunların hər biri üçün ayrıca state saxlamaq interfeysi proqnozlaşdırıla bilən edir.

  • loading — spinner göstər
  • error — anlaşıqlı mesaj göstər
  • data — uğurlu nəticəni render et
05 / 06

async / await React kontekstində

useEffect-in callback funksiyası özü async ola bilməz — çünki React ondan funksiya (cleanup) qaytarılmasını gözləyir, Promise yox. Buna görə daxildə ayrıca async funksiya yaradılır.

  • try / catch / finally strukturu
  • Xətanı tuturuq, işi "finally"-də bitiririk
06 / 06

Race condition problemi

İstifadəçi tez-tez parametr dəyişdirdikdə (məs. axtarış, ID) əvvəlki sorğu sonradan cavab qaytara və yeni məlumatın üstünü köhnə ilə örtə bilər.

  • Cleanup flag (ignore) üsulu
  • AbortController ilə sorğunu ləğv etmək

Loading / error / success — tam nümunə

async / await — tez-tez rast gəlinən səhv

Niyə? React useEffect-dən ya heç nə, ya da cleanup funksiyası qaytarılmasını gözləyir. async funksiya isə həmişə Promise qaytarır — bu, React-i çaşdırır və xəbərdarlıq (warning) yaradır.

Race condition — iki həll yolu

Fərz edək ki, istifadəçi userId parametrini sürətlə dəyişir (məsələn siyahıdan başqa profilə klikləyir). Əvvəlki sorğu gecikə bilər və sonradan qayıdıb yeni datanın üstünü köhnə ilə örtə bilər. Bunun qarşısını iki üsulla almaq olar:

1. Cleanup flag (ignore) üsulu

2. AbortController üsulu

Fərq: ignore üsulu sadədir, amma sorğu artıq göndərilmiş olur (nəticəni sadəcə nəzərə almırıq). AbortController isə şəbəkə sorğusunu real mənada ləğv edir — trafik və server resursuna qənaət edir.

04 · FAQ

Tez-tez verilən suallar

Kursda bu mövzu ilə bağlı ən çox verilən suallar və ətraflı cavablar.

GET Fetch çağırışını komponentin harasında etmək düzgündür?

Yalnız useEffect daxilində. Əgər fetch çağırışını birbaşa komponentin gövdəsində (render zamanı) yerləşdirsən, hər render zamanı yeni sorğu göndəriləcək — və sorğunun nəticəsi state-i dəyişdirdiyi üçün bu, yeni render yaradıb sonsuz dövrə səbəb olacaq.

İstisna: istifadəçinin klikləməsi kimi bir hadisə (event handler) daxilində fetch çağırmaq tamamilə düzgündür — məsələn "Yadda saxla" düyməsinə basılanda POST sorğusu göndərmək. Fərq ondadır ki, bu halda sorğu render zamanı deyil, konkret hərəkətə cavab olaraq gedir.

PUT Race condition necə həll olunur (cleanup, AbortController)?

Yuxarıda ətraflı izah olunduğu kimi, iki əsas üsul var: cleanup flag (let ignore = false, useEffect təmizlənəndə true edilir və nəticə tətbiq olunmur) və AbortController (sorğunu fiziki olaraq ləğv edir).

Praktik tövsiyə: kiçik layihələrdə ignore flag kifayət edir, çünki sadədir. İstifadəçi sürətlə axtarış edən (search-as-you-type) interfeyslərdə isə AbortController daha yaxşıdır, çünki lazımsız sorğular şəbəkəni yükləməzdən əvvəl dayandırılır.

DELETE Xəta baş verərsə istifadəçiyə necə düzgün mesaj göstərmək olar?

Üç qaydaya əməl et:

1) Texniki xəta mətnini (stack trace, "Network Error" kimi) birbaşa istifadəçiyə göstərmə — onun əvəzinə anlaşıqlı, insan dilində mesaj yaz: "Məlumatları yükləmək mümkün olmadı, bir az sonra yenidən cəhd edin."

2) Xətanın növünə görə fərqləndir: şəbəkə xətası (internet yoxdur), 404 (tapılmadı), 500 (server problemi) — hər biri üçün fərqli mesaj daha faydalıdır.

3) Əsl texniki xətanı isə console.error(err) ilə developer üçün konsola yaz ki, debug etmək asan olsun. Mümkünsə "Yenidən cəhd et" düyməsi əlavə et.

POST useEffect asılılıq massivini niyə düzgün doldurmaq vacibdir?

Asılılıq massivi React-ə deyir: "bu dəyərlərdən biri dəyişəndə effekti təkrar işə sal". Əgər effekt daxilində istifadə olunan bir dəyəri (məsələn userId) massivə əlavə etməsən, effekt köhnə dəyərlə "qıfıllanmış" (stale closure) qalar və ID dəyişəndə belə köhnə istifadəçini göstərməyə davam edər.

PATCH Niyə development rejimində sorğu iki dəfə göndərilir?

Bu bug deyil. React 18-in Strict Mode rejimi development zamanı komponentləri qəsdən mount → unmount → mount edir ki, təmizlənməmiş effektləri (yəni cleanup-u unudulmuş kodları) tez aşkar etsin. Production build-də bu davranış olmur, sorğu yalnız bir dəfə gedir. Əgər cleanup funksiyanı düzgün yazmısansa (yuxarıdakı race condition nümunələrinə bax), bu heç bir problem yaratmır.

05 · Diqqət

Olası xətalar və buglar

API inteqrasiyası zamanı tələbələrin ən çox rastlaşdığı problemlər — səbəbi və həlli ilə birlikdə.

INFINITE_LOOP

Sonsuz sorğu dövrü

Səbəb

useEffect-in asılılıq massivi unudulub, ya da massivə obyekt/funksiya kimi hər render-də yeni yaranan bir dəyər verilib.

Həll

Massivi boş qoy ([]) və ya yalnız primitiv dəyərlər (id, string) əlavə et; funksiyaları useCallback ilə sabitləşdir.

STRICT_MODE_2X

Effekt iki dəfə işə düşür

Səbəb

Development rejimində React Strict Mode effektləri qəsdən iki dəfə çağırır (bax: FAQ).

Həll

Narahat olma — production-da baş vermir. Amma cleanup funksiyasının düzgün yazıldığından əmin ol.

RACE_CONDITION

Köhnə sorğu yeni datanı əvəz edir

Səbəb

Parametr (məs. ID) sürətlə dəyişir, əvvəlki sorğu gecikərək sonradan qayıdır və son nəticəni üstələyir.

Həll

ignore flag və ya AbortController istifadə et.

UNMOUNTED_STATE

"Can't perform state update on unmounted component"

Səbəb

Komponent artıq DOM-dan silinib, amma hələ də cavab gözlənilən sorğu setState çağırmağa çalışır.

Həll

Cleanup funksiyasında flag təyin et, ya da AbortController ilə sorğunu ləğv et.

CORS_BLOCKED

CORS xətası

Səbəb

Brauzer başqa domenə göndərilən sorğunu təhlükəsizlik səbəbindən bloklayır, çünki server müvafiq CORS header-lərini qaytarmır.

Həll

Server tərəfdə Access-Control-Allow-Origin header-i əlavə edilməli. Test üçün JSONPlaceholder kimi API-lər CORS-a artıq icazə verir.

MISSING_CATCH

Xəta tutulmur, səssiz uğursuzluq

Səbəb

try/catch yazılmayıb və ya .catch() unudulub — sorğu uğursuz olanda istifadəçi heç nə görmür, konsolda "Unhandled promise rejection" xəbərdarlığı çıxır.

Həll

Hər async fetch əməliyyatını try/catch ilə əhatə et və error state-i istifadəçiyə göstər.

NO_LOADING_STATE

Loading state-i unutmaq

Səbəb

Sorğu davam edərkən ekran boş qalır, istifadəçi tətbiqin "asılıb" olduğunu düşünə bilər.

Həll

loading state-i əlavə et və spinner və ya skeleton göstər.

MISSING_KEY

.map() zamanı key prop unudulub

Səbəb

Massiv render edilərkən hər elementə unikal key verilmir — React konsolda xəbərdarlıq verir və render performansı zəifləyə bilər.

Həll

Hər elementə unikal, sabit ID ver: key={user.id} (index-dən qaçın, xüsusən sıralama dəyişəndə).

NULL_REFERENCE

"Cannot read properties of undefined"

Səbəb

İlkin state undefined təyin olunub, amma render zamanı üzərində .map() çağırılıb — data hələ gəlməyib.

Həll

İlkin state-i həmişə düzgün tipdə təyin et: useState([]), obyekt gözlənirsə useState(null) və render-də yoxlama et.

06 · Növbəti addım

Nələri etsək daha yaxşı olar

Tapşırığı bitirdikdən sonra kodu daha da təkmilləşdirmək üçün faydalı adətlər.

↺

Custom hook — useFetch()

Fetch məntiqini useUsers() kimi ayrıca hook-a çıxarmaq kodun təkrarını azaldır və komponenti sadə saxlayır.

⚡

React Query / SWR

Böyük layihələrdə caching, avtomatik refetch, retry və "stale-while-revalidate" strategiyasını əl ilə yazmaq əvəzinə hazır kitabxanadan istifadə et.

🔧

Axios instance + interceptors

Mərkəzləşdirilmiş baseURL, auth token əlavə etmək və xətaları bir yerdə idarə etmək üçün Axios interceptor-larından istifadə et.

⏱

Axtarışı debounce et

İstifadəçi yazarkən hər hərfdən sonra sorğu göndərmək əvəzinə, 300-500ms gecikmə ilə (debounce) sorğu göndər — server yükünü azaldar.

▦

Skeleton loading

Sadə spinner əvəzinə, gələcək kontentin formasını təqlid edən skeleton komponentləri UX-i daha "hamar" edir.

⛨

Error Boundary əlavə et

Render zamanı gözlənilməz xətaların bütün tətbiqi çökdürməsinin qarşısını almaq üçün Error Boundary komponenti istifadə et.

🔑

Environment dəyişənləri

API URL-lərini kodda hardcode etmə — .env faylında saxla (VITE_API_URL və s.), mühitlər arasında keçidi asanlaşdır.

TS

TypeScript ilə tip təhlükəsizliyi

API-dən gələn cavabın formasını interface User {} kimi təyin etmək səhvləri kompilyasiya mərhələsində tutur.
