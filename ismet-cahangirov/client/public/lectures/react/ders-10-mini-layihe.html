01

Kod təşkili: qovluq strukturu və adlandırma

Layihə böyüdükcə, "hər şeyi src-in içinə atmaq" strategiyası tez bir zamanda xaosa çevrilir. Yaxşı qovluq strukturu — sadəcə səliqə üçün deyil, komandada işləyərkən başqasının (və ya 3 ay sonra özünüzün) kodu tez tapa bilməsi üçündür.

01.1Tövsiyə olunan qovluq strukturu

Kiçik-orta ölçülü layihələr üçün "növə görə" (type-based) struktur ən başa düşülən variantdır:

src/
src/
├── components/       // yenidən istifadə olunan UI hissələri
│   ├── Button.jsx
│   ├── TaskCard.jsx
│   └── Navbar.jsx
├── pages/            // marşrutlara uyğun tam səhifələr
│   ├── HomePage.jsx
│   ├── TaskDetailPage.jsx
│   └── NotFoundPage.jsx
├── hooks/            // öz custom hook-larınız
│   ├── useFetch.js
│   └── useLocalStorage.js
├── context/          // Context provider-lər
│   └── ThemeContext.jsx
├── services/         // API çağırışları bir yerdə
│   └── taskApi.js
├── utils/            // köməkçi funksiyalar (formatDate və s.)
├── styles/
├── App.jsx
└── main.jsx

Layihə daha da böyüyəndə (10+ səhifə, bir neçə komanda üzvü) "feature-based" struktura keçmək məntiqlidir — yəni src/features/tasks/, src/features/auth/ kimi, hər xüsusiyyətin öz komponenti, hook-u və API çağırışı bir qovluqda yaşayır. Kursu bitirən kimi buna ehtiyacınız olmayacaq, amma bunun mövcud olduğunu bilmək vacibdir.

01.2Adlandırma qaydaları

Komponentlər

PascalCase

TaskCard.jsx, UserProfile.jsx. Fayl adı komponentin adı ilə tam üst-üstə düşməlidir — axtaranda dərhal tapılsın.

Custom hook-lar

camelCase, "use" ilə başlayır

useFetch.js, useTheme.js. "use" prefiksi React-a bu funksiyanın hook qaydalarına tabe olduğunu bildirir.

Adi funksiyalar/dəyişənlər

camelCase

formatDate(), taskList. Sabitlər üçün (dəyişməyən konfiqurasiya dəyərləri) UPPER_SNAKE_CASE istifadə olunur.

index.js barrel fayllar

Ehtiyatla istifadə edin

Hər qovluqda index.js ilə re-export etmək rahatdır, amma həddindən artıq istifadə edildikdə "hansı fayl haradan gəlir" izləmək çətinləşir.

02

Ümumi başlanğıc səhvlərinin təkrarı

Kurs boyu keçdiyimiz 10 dərsin ən çox rastlanan səhvlərini bir yerə topladıq. Bunları tanımaq, onlardan qaçmaqdan daha vacibdir — çünki hər developer bunları edir, önəmli olan tez tanıyıb düzəltməkdir.

Dərs 3-4

Siyahıda key unudulması

.map() ilə render edərkən key prop-unu buraxmaq — React-ın hansı elementin dəyişdiyini izləməsini pozur, silmə/sıralama zamanı qəribə UI xətalarına səbəb olur.

Dərs 5

State-i birbaşa mutasiya etmək

state.push(item) əvəzinə həmişə yeni massiv/obyekt qaytarın: setState([...state, item]). Əks halda komponent yenidən render olunmaya bilər.

Dərs 6

useEffect-də asılılıq massivi səhvləri

Boş [] qoyub içəridə dəyişən dəyişəndən istifadə etmək (stale closure), yaxud asılılığı tam qoymayıb sonsuz render dövrəsi yaratmaq — ən çox baş verən bug mənbəyidir.

Dərs 4-7

Props drilling

Dəyəri 4-5 səviyyə aşağı komponentə ötürmək üçün hər aralıq komponentdən keçirmək. Bu, Context və ya state management alətinin nə üçün mövcud olduğunu göstərir.

Dərs 3

Event handler-ı dərhal çağırmaq

onClick={handleClick()} yazmaq — bu, render zamanı funksiyanı dərhal işə salır. Düzgünü: onClick={handleClick} və ya onClick={() => handleClick(id)}.

Dərs 3

Şərti render-də 0 problemi

{count && <Badge />} — count 0 olduqda ekranda "0" rəqəmi görünür. Düzgünü: {count > 0 && ...} və ya ternary istifadə edin.

Dərs 7

Loading/error state-in unudulması

API çağırışı zamanı yalnız uğurlu nəticəni gözləmək. İstifadəçi yavaş internetdə, yaxud server xətasında boş/qırıq ekranla qarşılaşır.

Dərs 8

Context-in həddindən artıq istifadəsi

Hər kiçik state üçün ayrı Context yaratmaq — hər dəyişiklikdə bütün ağacın yenidən render olunmasına səbəb ola bilər.

03

State idarəetmənin növbəti səviyyəsi

useState və Context API kiçik-orta layihələr üçün kifayətdir. Amma tətbiq böyüdükdə, çoxlu komponent eyni state-i paylaşdıqda və dəyişiklik tarixçəsini izləmək lazım gəldikdə, xüsusi bir alət lazım olur. İki ən populyar seçim: Redux Toolkit və Zustand.

Redux Toolkit

Struktur və nəzarət üçün

Redux-un rəsmi, "boilerplate-i azaldılmış" versiyası. Ciddi qaydalar (action, reducer, slice), Redux DevTools ilə vaxtda geriyə getmə (time-travel debugging), böyük komandalar üçün proqnozlaşdırıla bilən struktur təqdim edir.

Zustand

Sadəlik və sürət üçün

Minimal boilerplate ilə hook-əsaslı state store. Provider "sarmağa" ehtiyac yoxdur, öyrənmə əyrisi qısadır. Kiçik-orta komanda və layihələr üçün əla seçimdir.

04

Next.js-ə giriş: React-dan fərqi

İndiyə qədər öyrəndiyiniz React (Vite ilə) — brauzerdə işləyən, "client-side rendering" (CSR) əsaslı bir kitabxanadır. Next.js isə React üzərində qurulmuş bir framework-dür və server-side imkanlar əlavə edir.

04.1SSR nədir və niyə vacibdir

Adi React tətbiqində brauzer boş bir HTML alır, sonra JavaScript yüklənir və səhifəni "qurur". Next.js isə HTML-i serverdə əvvəlcədən render edir (Server-Side Rendering) — istifadəçi dərhal məzmunu görür, axtarış motorları (Google) səhifəni daha yaxşı indeksləyir.

04.2File-based routing

React Router-də marşrutları əl ilə kod içində təsvir edirsiniz. Next.js-də isə qovluq strukturu birbaşa marşrutu müəyyən edir:

        └── page.jsx    // → "/tasks/12" (dinamik)

05

Praktiki hissə: Mini-layihə

Kursun bütün mövzularını bir tətbiqdə birləşdirəcəyik: To-Do List + API inteqrasiyası + Routing + Context (tema). Aşağıda tam texniki spesifikasiya və addım-addım tikinti planı var.

05.1Funksional tələblər

1. Tapşırıqlar (CRUD)

Tapşırıq əlavə etmək, redaktə etmək, silmək, "tamamlandı" işarələmək. Vəziyyəti useReducer ilə idarə etmək tövsiyə olunur — çoxlu əlaqəli əməliyyat olduğundan.

2. API inteqrasiyası

Tapşırıqları xarici mənbədən (məs. JSONPlaceholder və ya öz mock API-niz) çəkin. Yükləmə (loading) və xəta (error) vəziyyətlərini istifadəçiyə göstərin.

3. Routing

Ən azı iki səhifə: siyahı (/) və tapşırığın detalı (/tasks/:id). React Router ilə naviqasiya qurun.

4. Context (tema)

Açıq/qaranlıq rejim arasında keçid. Seçim localStorage-də saxlanmalı ki, səhifə yenilənəndə itməsin.

05.2Tikinti sırası (addım-addım)

  • 1-ci addım — Vite ilə layihəni yaradın, qovluq strukturunu 01-ci bölmədəki nümunəyə uyğun qurun.
  • 2-ci addım — Statik komponentləri qurun: TaskCard, TaskList, Navbar — hələ data olmadan, sadəcə görünüş.
  • 3-cü addım — ThemeContext-i yaradın və App.jsx-i onunla sarın — bu ən sadə hissədir, əvvəl bitirin ki, motivasiya düşməsin.
  • 4-cü addım — services/taskApi.js daxilində API funksiyalarını yazın (getTasks, addTask və s.).
  • 5-ci addım — useFetch custom hook-u ilə data çəkməni, loading/error idarəetməsini bir yerə toplayın.
  • 6-cı addım — React Router-i qurun, TaskDetailPage-i dinamik :id parametri ilə bağlayın.
  • 7-ci addım — CRUD əməliyyatlarını useReducer ilə bağlayın, formanı test edin.
  • 8-ci addım — Kiçik "cilalama": boş siyahı mesajı, uğurlu/uğursuz bildirişlər, responsive CSS.
src/context/ThemeContext.jsx
import { createContext, useState, useEffect } from 'react';

export const ThemeContext = createContext();

export function ThemeProvider({ children }) {
  const [theme, setTheme] = useState(
    () => localStorage.getItem('theme') || 'light'
  );

  useEffect(() => {
    localStorage.setItem('theme', theme);
  }, [theme]);

  const toggleTheme = () =>
    setTheme(prev => (prev === 'light' ? 'dark' : 'light'));

  return (
    <ThemeContext.Provider value={{ theme, toggleTheme }}>
      {children}
    </ThemeContext.Provider>
  );
}

07

Xəta və bug bələdçisi

Mini-layihəni qurarkən qarşınıza çıxa biləcək ən çox yayılmış xətalar və onların həlli. Bunları qarşıdan gördükdə paniki etməyin — demək olar hər developer bu siyahını dəfələrlə görür.

"Cannot read properties of undefined"

SəbəbAPI cavabı hələ gəlməyib, amma komponent artıq data-nı oxumağa çalışır.
HəllLoading state yoxlayın; data?.title kimi optional chaining istifadə edin.

Sonsuz render dövrəsi

SəbəbuseEffect içində state yeniləyib, asılılıq massivinə həmin state-i yanlış əlavə etmək, ya da hər renderdə yeni obyekt/massiv yaratmaq.
HəllAsılılıqları diqqətlə seçin; obyekt/funksiyaları useMemo/useCallback ilə sabitləyin.

CORS xətası

SəbəbXarici API brauzerdən birbaşa sorğuya icazə vermir.
HəllCORS dəstəkləyən test API istifadə edin, və ya öz kiçik backend/proxy qurun.

Səhifə yenilənəndə 404 (routing)

Səbəb/tasks/3 ünvanını birbaşa açanda server bu marşrutu tanımır (Vite/statik hosting konfiqurasiyası).
HəllHosting platformasında SPA "fallback to index.html" qaydasını aktivləşdirin (Vercel/Netlify-də avtomatik dəstəklənir).

Tema seçimi yadda saxlanmır

SəbəblocalStorage ilə sinxronizasiya unudulub, yalnız React state-də saxlanılır.
HəllTema dəyişəndə useEffect ilə localStorage.setItem çağırın (05.2-dəki nümunəyə baxın).

"Can't perform a React state update on an unmounted component"

SəbəbKomponent DOM-dan silinəndən sonra hələ tamamlanmamış fetch cavabı state-i yeniləməyə çalışır.
HəlluseEffect-də cleanup funksiyası ilə sorğunu ləğv edin, yaxud "mounted" bayrağı istifadə edin.

09

Tez-tez verilən suallar

Q1 React öyrəndikdən sonra hansı istiqamətə getmək lazımdır?

Bu, tam olaraq məqsədinizdən asılıdır. Üç əsas yol var, aşağıdakı yol xəritəsi bölməsində vizual şəkildə göstərilib:

Next.js — SEO vacib olan, ictimaiyyətə açıq veb saytlar (bloq, e-ticarət, marketinq səhifələri) qurmaq istəyirsinizsə. React Native — mobil tətbiq (iOS/Android) inkişaf etdirmək istəyirsinizsə, React bilikləriniz birbaşa işə yarayır. TypeScript isə əslində "alternativ" deyil — bu, hər iki yolla da birləşən, kod keyfiyyətini artıran bir vasitədir. Əksər iş elanlarında TypeScript tələb olunduğu üçün, hansı istiqaməti seçsəniz seçin, TypeScript-i öyrənmək güclü tövsiyədir.

Q2 Real layihələrdə hansı state management alətini seçmək lazımdır?

Universal cavab yoxdur — qərar bu suallara görə verilir:

Layihə kiçikdirsə (bir neçə səhifə, kiçik komanda) — useState + Context adətən kifayətdir. Komanda böyükdürsə və state çox mürəkkəbdirsə (məs. çoxlu asılı əlaqələr, vaxtda geriyə debug etmək tələbi) — Redux Toolkit. Sürətli inkişaf lazımdırsa, komanda kiçikdirsə, boilerplate istəmirsinizsə — Zustand. İş bazarını nəzərə alsanız, Redux Toolkit hələ də ən çox tələb olunan bacarıqlardan biridir, ona görə heç olmasa əsaslarını bilmək faydalıdır.

Q3 Portfolio üçün hansı layihələr edilməlidir?

İşəgötürənlər eyni "to-do list" layihəsini yüzlərlə görür — seçdiyiniz layihə real bir problemi həll etməli və API/state idarəetməsini nümayiş etdirməlidir:

Hava proqnozu tətbiqi — xarici API, axtarış, loading/error idarəetməsi. Kiçik e-ticarət vitrini — məhsul siyahısı, filter, səbət state-i (Context və ya Zustand). Şəxsi bloq/CMS — Next.js ilə SSR, dinamik marşrutlar. Məlumat paneli (dashboard) — qrafiklər, cədvəllər, real API ilə. Söhbət (chat) tətbiqi — real-vaxt data (WebSocket və ya Firebase) ilə tanışlıq. Ən vacibi: hər layihədə README, təmiz kod strukturu və canlı demo linki olsun.
