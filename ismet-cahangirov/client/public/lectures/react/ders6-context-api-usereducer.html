Context API, useReducer və Prop Drilling

Komponentlər arasında props ötürmədən qlobal state idarə etməyi öyrənirik — nəzəriyyədən praktikaya, bütün tələ və xətaları ilə birlikdə.

⏱ ~2.5 saat 🎯 Tapşırıq: Dark/Light Mode Context 📦 Ön şərt: useState, useEffect
💡 Sınayın: yuxarı sağdakı düyməni klikləyin. Bütün səhifənin rəngi, kod bloklarının rəngi, hər şey bir anda dəyişəcək — heç bir prop heç yerə ötürülmədi. Məhz bunu bu dərsdə Context API vasitəsilə necə qurduğumuzu öyrənəcəyik.

📘 Nəzəri hissə

1. Giriş

Bu dərsdə React tətbiqlərində state paylaşma probleminin iki əsas həllini öyrənəcəyik: Context API və useReducer. Hər ikisi də "state böyüdükcə komponentləri necə təmiz saxlayaq" sualına cavab verir, sadəcə fərqli tərəflərdən.

Dərs iki hissədən ibarətdir:

  • Nəzəri hissə (~60 dəq): Prop drilling problemi, Context API-nin quruluşu, useReducer hook-u, useReducer və useState arasındakı fərq, qlobal state prinsipləri.
  • Praktiki hissə (~90 dəq): Dark/Light tema üçün real Context yaratmaq və səbət (cart) state-ini useReducer ilə idarə etmək.
📎 Ön şərtlər

Bu dərsi başa düşmək üçün useState, useEffect və komponentlərin bir-birinə props ötürməsi haqqında əsas biliyiniz olmalıdır. Əgər bu mövzularda özünüzü əmin hiss etmirsinizsə, əvvəlki dərslərə qayıtmaq faydalı olar.

📘 Nəzəri hissə

2. Prop Drilling Problemi

Prop drilling — bir state-i komponent ağacının yuxarısından çox aşağıdakı bir komponentə çatdırmaq üçün, aralıqdakı bütün komponentlərdən məcburi keçirməyə deyilir. Aralıq komponentlərin həmin data ilə heç bir işi olmasa belə, onu sadəcə "ötürmək" üçün qəbul etməli olurlar.

Nümunə: pis ssenari

Tutaq ki, istifadəçi məlumatını yalnız ən dərində yerləşən Avatar komponentində göstərmək istəyirik. Amma Layout, Sidebar və UserPanel komponentləri bu data ilə heç nə etmir — sadəcə ötürücü rolundadırlar:

App.jsx — prop drilling nümunəsi

Diqqət edin: user propu 4 səviyyədən keçir, amma yalnız birinci (App) və sonuncu (Avatar) komponent onunla real işləyir. Layout, Sidebar və UserPanel yalnız "kuryer" rolunu oynayır.

Context ilə Provider dəyəri istənilən dərinlikdəki komponentə birbaşa "yayımlanır" (broadcast) — aralıq komponentlər ondan xəbərsiz qalır.

Prop drilling nə vaxt real problemdir?

Hər prop ötürmə "pis" deyil — 1-2 səviyyəlik ötürmə tamamilə normaldır və Context-ə ehtiyac yoxdur. Problem böyüyür, çünki:

  • Ağac 3-4 səviyyədən dərin olanda kod oxunması çətinləşir.
  • Aralıq komponentləri refaktor etmək (adını dəyişmək, yerini dəyişmək) prop zəncirini qırır.
  • Data haradan gəldiyini izləmək çətinləşir ("bu user harada təyin olunub?").
  • Aralıq komponentlərin propType-larına lazımsız "keçici" sahələr əlavə olunur.
💡 Alternativ: composition (children pattern)

Context yeganə həll deyil. Bəzən komponentləri children prop-u ilə "yerləşdirmək" (composition) prop drilling-i tamamilə aradan qaldırır, çünki aralıq komponent uşaq elementi tanımır, sadəcə göstərir. Context əsasən geniş yayılmış, "qlobal" sayılan data (tema, dil, autentifikasiya) üçün ən yaxşı seçimdir.

4. useReducer Hook-u

useReducer — mürəkkəb state məntiqini idarə etmək üçün useState-in alternatividir. Onun məntiqi Redux-dan gəlir: state-i birbaşa dəyişmək əvəzinə, siz nə baş verdiyini (action) bildirirsiniz, "reducer" funksiyası isə həmin action-a əsasən yeni state hesablayır.

Sintaksis
  • reducer — (state, action) => yeniState imzasına malik sırf (pure) funksiya. Heç vaxt köhnə state-i mutasiya etmir, hər zaman yeni obyekt qaytarır.
  • initialState — başlanğıc state dəyəri.
  • state — hazırkı state (oxumaq üçün).
  • dispatch — action "göndərmək" üçün funksiya: dispatch({ type: "ADD_ITEM", payload: {...} }).

Nümunə: səbət (cart) reducer

Diqqət: switch-in hər case-i state-i mutasiya etmir — { ...state, items } kimi tamamilə yeni obyekt qaytarır. Bu, React-in dəyişikliyi görməsi üçün vacibdir.

📎 Action necə "göndərilir"?

dispatch({ type: "ADD_ITEM", payload: product }) çağırıldıqda React avtomatik olaraq reducer funksiyasını (cariState, bu_action) ilə çağırır, qaytarılan nəticəni yeni state kimi saxlayır və komponenti yenidən render edir.

Əgər state-in 3-dən çox bir-biri ilə bağlı sahəsi varsa, yaxud "növbəti state necə hesablanır?" sualının cavabı bir neçə şərtdən asılıdırsa — useReducer-ə keçin. Sadə bayraq, mətn sahəsi və ya say üçün useState tamamilə kifayətdir.

6. Qlobal State İdarəetməsinin Əsas Prinsipləri

  • Single source of truth: hər data parçasının yalnız bir "əsl mənbəyi" olmalıdır — onu bir neçə yerdə dublikat saxlamayın.
  • Immutability (dəyişməzlik): state-i heç vaxt birbaşa mutasiya etməyin (state.items.push(...) YOX). Həmişə yeni obyekt/massiv qaytarın ([...state.items, yeni]).
  • Unidirectional data flow: data yuxarıdan aşağı axır (props/context), hadisələr (action-lar) aşağıdan yuxarı axır (dispatch/callback). Bu axını qarışdırmayın.
  • Minimal state: yalnız həqiqətən lazım olanı state-də saxlayın. Başqa state-lərdən hesablana bilən dəyərləri (məs. cəmi, say) render zamanı hesablayın, ayrıca state kimi saxlamayın.
  • Separation of concerns: state məntiqini (reducer) UI-dan ayırın — bu, həm oxunaqlılığı, həm test edilə bilməni artırır.
🛠 Praktiki hissə

7. Praktiki: Tema (Dark/Light) Context-i

İndi addım-addım quraq:

  1. Context yaradın — createContext(null) ilə boş kanal açın.
  2. Provider komponenti yazın — daxilində useState ilə temanı saxlayın, dəyişdirmək üçün funksiya yazın.
  3. Dəyəri useMemo ilə "sabitləyin" — hər render-də yeni obyekt yaratmasın (səbəbini "Xətalar" bölməsində görəcəyik).
  4. Custom hook yazın (useTheme) — Provider-dən kənar istifadəni yaxalasın.
  5. Tətbiqi Provider ilə bürüyün — adətən ən yuxarı səviyyədə, App.jsx-da.
  6. İstənilən komponentdə istifadə edin — const { theme, toggleTheme } = useTheme().

3-cü addımın koda uyğun tam nümunəsi 3-cü bölmədə (Context API-nin Quruluşu) verilib. CSS tərəfində isə tema adətən bir data-theme atributu və CSS dəyişənləri (custom properties) ilə tətbiq olunur — məhz bu səhifədə istifadə etdiyimiz üsul budur:

    🎯 Tapşırıq

    9. Tapşırıq: Dark/Light Mode Toggle Bütün Tətbiq Üzrə

    Öz React tətbiqinizdə (və ya kiçik bir nümunə layihədə) aşağıdakıları həyata keçirin:

    Tələblər

    • ThemeContext.jsx faylında createContext, ThemeProvider və useTheme custom hook-unu yazın.
    • App.jsx-da bütün tətbiqi ThemeProvider ilə bürüyün.
    • Ən azı 3 fərqli komponentdə (məs. Header, Sidebar, Footer) heç bir prop qəbul etmədən useTheme() vasitəsilə temaya müraciət edin.
    • Toggle düyməsi ilə light ↔ dark arasında keçid təmin edin.
    • Temanı CSS dəyişənləri (custom properties) və ya conditional className ilə tətbiq edin.
    • Provider-in value obyektini useMemo ilə optimallaşdırın.

    Bonus (əlavə xal üçün)

    • Seçilmiş temanı emoji/ikon ilə göstərin (🌙 / ☀️).
    • İlkin temanı window.matchMedia('(prefers-color-scheme: dark)') ilə sistem seçiminə uyğun təyin edin.
    • Tema dəyişəndə keçidə yumşaq CSS transition əlavə edin.
    ⚠️ Diqqət

    Tapşırıqda heç bir komponentə theme propu manual ötürülməməlidir. Əgər hər hansı komponentdə <Sidebar theme={theme} /> kimi bir şey görürsünüzsə, deməli, Context düzgün istifadə olunmayıb.

    ⚠️ Ola bilən xətalar və buglar

    10. Tez Rast Gəlinən Xətalar

    1. Provider unudulur

    Komponent useContext çağırır, amma ağac heç bir Provider ilə bürünməyib. Nəticədə context dəyəri createContext()-də verilən default (adətən null) olur, komponent isə səssizcə səhv işləyir.

    Həll

    Custom hook daxilində if (!context) throw new Error(...) yoxlaması qoyun ki, xəta erkən və aydın görünsün.

    2. Hər render-də yeni value obyekti

    <Context.Provider value={{ theme, toggleTheme }}> yazsanız, hər render-də yeni obyekt yaranır — bu, dəyər dəyişməsə belə, bütün consumer-lərin yenidən render olunmasına səbəb olur.

    Həll

    useMemo(() => ({ theme, toggleTheme }), [theme]) ilə dəyəri yalnız theme dəyişəndə yenidən yaradın.

    3. State-in birbaşa mutasiyası

    Reducer daxilində state.items.push(...) və ya state.count++ kimi birbaşa dəyişiklik etmək — React dəyişikliyi tanımır, çünki obyektin referansı eyni qalır.

    Həll

    Həmişə yeni obyekt/massiv qaytarın: { ...state, items: [...state.items, item] }.

    4. Default dəyər olmadan createContext()

    createContext() boş çağırılanda TypeScript layihələrində tip xətaları, JS layihələrində isə "undefined-a müraciət" xətaları yarana bilər.

    Həll

    Ya mənalı bir default dəyər verin, ya da null verib custom hook-da yoxlayın (yuxarıdakı 1-ci bənd kimi).

    5. dispatch-i sinxron zənn etmək

    dispatch(action) çağırdıqdan dərhal sonra state-i oxuyub "yeniləndi" güman etmək — React state yeniləmələri batch (toplu) şəkildə, növbəti render-də tətbiq olunur.

    Həll

    Yeni dəyərə əsaslanan məntiqi useEffect daxilində və ya reducer-in özündə həyata keçirin, dispatch-dən dərhal sonra deyil.

    6. switch-də break/return unudulması

    Reducer-in switch blokunda bir case-dən return etməsəniz, icra növbəti case-ə "sızır" (fall-through) və gözlənilməz state yaranır.

    Həll

    Hər case-i mütləq return ilə bitirin, defensiv olaraq default: return state; həmişə əlavə edin.

    7. Nested Provider-lərin sırası

    Bir-birindən asılı olan Context-ləri (məs. AuthProvider daxilindən theme-ə görə fərqli render) səhv sırada yerləşdirmək gözlənilməz nəticələrə səbəb ola bilər.

    Həll

    Provider-lərin iyerarxiyasını (hansı hansından asılıdır) əvvəlcədən planlaşdırın, lazım gələrsə bir AppProviders komponentində birləşdirin.

    8. Hook-un şərtli çağırılması

    if blokunun içində və ya erkən return-dən sonra useContext/useReducer çağırmaq — React Hooks qaydalarını pozur və "Rendered more hooks than expected" xətası verir.

    Həll

    Bütün hook-ları həmişə komponentin ən yuxarısında, şərtsiz çağırın; şərti məntiqi hook-dan sonra yazın.

    ✅ Yaxşı təcrübələr

    11. Nələri Etsək Daha Yaxşı Olar

    Həmişə custom hook yaradın

    Komponentlərdə birbaşa useContext(ThemeContext) yazmaq əvəzinə, useTheme() kimi öz hook-unuzu yazın. Bu, həm xəta yoxlamasını, həm gələcək dəyişiklikləri asanlaşdırır.

    Context-i "concern"ə görə bölün

    Bir nəhəng AppContext yaratmaq əvəzinə, ThemeContext, AuthContext, CartContext kimi ayrı-ayrı, kiçik context-lər yaradın — yalnız əlaqədar komponentlər yenidən render olunur.

    Provider value-nu memoize edin

    useMemo (obyekt üçün) və useCallback (funksiyalar üçün) istifadə edərək Provider-in value propunu hər render-də yenidən yaratmaqdan çəkinin.

    Reducer və action-ları ayırın

    Reducer funksiyasını və action tiplərini (const CART_ACTIONS = {...}) ayrı fayla çıxarın. Bu, həm test etməyi, həm oxunaqlılığı artırır və "sehrli sətir" (magic string) xətalarının qarşısını alır.

    Reducer-i sırf funksiya saxlayın

    Reducer daxilində API çağırışı, setTimeout və ya digər yan effektlər (side effects) etməyin — bu, onu test edilməz və proqnozlaşdırılmaz edir. Yan effektləri useEffect-də saxlayın.

    Nə vaxt Redux/Zustand-a keçməli olduğunuzu bilin

    Əgər state tez-tez dəyişir, çoxlu komponent onu oxuyur və performans kritikdirsə, seçici (selector) əsaslı kitabxanalar (Zustand, Redux) daha yaxşı miqyaslanır. Bunu FAQ bölməsində ətraflı müzakirə edirik.

    ❓ Tez-tez verilən suallar

    12. FAQ

    Context nə vaxt Redux/Zustand-ı əvəz edə bilər, nə vaxt yox?

    Context yaxşı işləyir: az dəyişən, "qlobal sayılan" data üçün — tema, dil, autentifikasiya olunmuş istifadəçi məlumatı. Kiçik-orta ölçülü tətbiqlərdə əlavə kitabxana quraşdırmadan qlobal state lazım olanda.

    Redux/Zustand daha uyğundur: state tez-tez dəyişəndə və yalnız müəyyən komponentlərin yenilənməsi vacib olanda — çünki bu kitabxanalar selector vasitəsilə yalnız lazımi hissəni "abunə edən" komponentləri render edir, halbuki Context-də dəyər dəyişdikdə bütün consumer-lər (memoizasiya olmasa) yenidən render olunur. Həmçinin böyük komandalarda konvensiya, DevTools və time-travel debugging lazım olanda bu kitabxanalar üstünlük verir.

    Qısaca: Context — "dependency injection" mexanizmidir, əsl state-idarəetmə kitabxanası deyil. useReducer + Context birləşməsi kiçik-orta layihələrdə Redux-a bənzər bir pattern verə bilər, amma performans üçün incə tənzimləmə imkanları məhduddur.

    useReducer-in useState-dən üstünlüyü nədir?

    Əsas üstünlük — mürəkkəb, çoxsahəli state keçidlərini bir yerdə mərkəzləşdirməkdir. Bir neçə sahə bir-biri ilə bağlı olanda (məs. səbətdə items dəyişəndə totalPrice də yenilənməlidir), reducer bu məntiqi bir funksiyada saxlayır və hər action üçün "nə baş verdiyini" adlandırılmış şəkildə (ADD_ITEM, CLEAR_CART) ifadə edir.

    Bundan başqa reducer sırf (pure) funksiya olduğu üçün komponentdən asılı olmadan asanlıqla test edilə bilir, və dəyişiklik tarixçəsini (action log) izləmək təbii şəkildə mümkün olur — məhz yuxarıdakı canlı demoda gördüyünüz kimi.

    Çoxlu Context istifadə etmək performansa təsir edirmi?

    Diqqətli olmaq lazımdır, amma məsələ adətən "neçə context" deyil, "value necə yaradılır" sualındadır. Bir Context-in value-su dəyişəndə, React.memo istifadə edilməyibsə, bütün həmin Context-i oxuyan komponentlər yenidən render olunur.

    Praktikada, bir neçə kiçik, "concern"ə görə bölünmüş context (ThemeContext, AuthContext, CartContext) — bir nəhəng, hər şeyi özündə saxlayan tək context-dən daha yaxşı performans verir, çünki yalnız əlaqədar komponentlər yenilənir. Əsl performans probleminin mənbəyi isə çox vaxt Provider-in value obyektini useMemo olmadan hər render-də yenidən yaratmaqdır (10-cu bölmədəki 2-ci xətaya baxın).

    📘 Yekun

    13. Yekun

    Bu dərsdə öyrəndik ki:

    • Prop drilling — data-nı lazımsız yerə çoxlu aralıq komponentdən keçirməkdir, və dərin ağaclarda kodun oxunaqlılığını azaldır.
    • Context API (createContext + Provider + useContext) qlobal sayılan data-nı prop ötürmədən istənilən dərinlikdəki komponentə çatdırır.
    • useReducer mürəkkəb, çoxsahəli state məntiqini bir yerdə — sırf reducer funksiyasında — mərkəzləşdirir.
    • Context + useReducer birləşməsi kiçik-orta tətbiqlərdə Redux-a bənzər bir qlobal state pattern-i verir.
    • Performans üçün Provider-in value-sunu useMemo/useCallback ilə sabitləmək, context-ləri concern-ə görə bölmək vacibdir.
