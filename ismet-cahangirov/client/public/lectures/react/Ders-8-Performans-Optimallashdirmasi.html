Nəzəri hissə

Render niyə "təkrarlanır"?

React-də performans problemlərinin demək olar hamısı bir kökdən qaynaqlanır: lazımsız yenidən render olunma. Əvvəlcə bunun niyə baş verdiyini anlayaq, sonra React-in verdiyi üç əsas alətlə — useMemo, useCallback, React.memo — bunu necə idarə edəcəyimizi öyrənək.

01

Lazımsız re-render-lərin yaranma səbəbləri

Component-in state və ya props-u dəyişəndə React onun funksiyasını yenidən çağırır — buna "render" deyilir. Render özü birbaşa DOM-u dəyişdirmir: React əvvəlcə yeni virtual DOM ağacını hesablayır, sonra onu əvvəlki ağacla müqayisə edir (reconciliation) və yalnız fərqi real DOM-a tətbiq edir. Problem odur ki, render funksiyasının özünün icrası da vaxt aparır — xüsusilə ağır hesablamalar olduqda və ya component ağacı böyük olduqda.

Ən çox rast gəlinən səbəblər:

  1. Parent render → bütün children render. Defolt olaraq, valideyn komponent render olunanda, onun bütün uşaq komponentləri də yenidən render olunur — props-ları heç dəyişməsə belə.
  2. State dəyişikliyi. useState / useReducer ilə idarə olunan state hər dəyişdikdə, o state-dən asılı olan komponent yenidən render olunur.
  3. Context dəyişikliyi. Bir Context Provider-in value-su dəyişəndə, həmin context-i "consume" edən bütün komponentlər render olunur — hətta onlar dəyərin yalnız bir hissəsindən istifadə etsələr belə.
  4. Hər renderdə yeni referans yaranması. JavaScript-də {}, [] və funksiyalar hər dəfə "yeni" obyekt kimi yaranır — məzmunu eyni olsa belə ({} !== {}). Render funksiyası daxilində "inline" yaradılan obyekt/array/funksiya propslar üçün bu, ciddi problemdir.
  5. Key prop-un səhv seçilməsi. Siyahılarda key kimi massiv index-indən istifadə etmək React-ə "hansı element həqiqətən dəyişib" sualını düzgün cavablandırmağa mane olur və lazımsız unmount/remount yaradır.
💡

Vacib fərq: render olunmaq DOM-un dəyişməsi demək deyil. React render nəticəsini əvvəlki ilə müqayisə edir və real DOM-a yalnız fərqi yazır. Amma müqayisənin özü və render funksiyasının icrası pulsuz deyil — optimallaşdırmanın hədəfi məhz budur.

Canlı simulyasiya

Render Laboratoriyası

Aşağıdakı simulyasiya real React tətbiqinin sadələşdirilmiş modelidir: iki "uşaq komponent" var — biri adi, digəri React.memo ilə sarılıb. Fərqli düymələri sınayıb, hansı halda hansının render olunduğunu izləyin.

Ana komponent render sayı: 0
<PlainChild /> — memo yoxdur Adi
0 render
Hələ heç bir hadisə baş verməyib
<MemoChild /> — React.memo Memo
0 render
Hələ heç bir hadisə baş verməyib

❄️ "Əlaqəsiz state-i dəyiş" ana komponentdə uşaqlara heç bir aidiyyəti olmayan bir state-i dəyişir (məsələn tema rəngi). Ana yenidən render olunur, adi uşaq da onunla birlikdə render olunur — React.memo ilə sarılmış uşaq isə props-u dəyişmədiyi üçün render-i "atlayır".
🔥 "Uşaq props-unu dəyiş" isə uşağa ötürülən real props-u dəyişir — bu halda hər iki uşaq render olunur, çünki bu dəfə dəyişiklik həqiqətən onlara aiddir.

02

useMemo — hesablamaların yaddaşda saxlanması

useMemo bir hesablamanın nəticəsini yaddaşda saxlayır və yalnız dependency array-dəki dəyərlər dəyişəndə həmin hesablamanı yenidən icra edir. Digər hallarda əvvəlki nəticəni birbaşa qaytarır.

❌ Problem
function ProductList({ products, query }) {
  // hər render-də — hətta əlaqəsiz
  // state dəyişəndə belə — təkrar hesablanır
  const filtered = products.filter(p =>
    p.name.toLowerCase().includes(query)
  );

  return filtered.map(p => <Item {...p} />);
}
✅ Həll
function ProductList({ products, query }) {
  const filtered = useMemo(() => {
    return products.filter(p =>
      p.name.toLowerCase().includes(query)
    );
  }, [products, query]);
  // yalnız bunlar dəyişəndə təkrar hesablanır

  return filtered.map(p => <Item {...p} />);
}

Nə vaxt istifadə etmək lazımdır:

  • Hesablama həqiqətən "baha"dırsa — böyük massiv üzərində sort, filter, reduce, mürəkkəb riyazi əməliyyatlar.
  • Nəticənin referensial olaraq stabil qalması lazımdırsa — məsələn, nəticə React.memo ilə sarılmış child-ə obyekt/array kimi ötürüləndə.
⚠️

Diqqət: useMemo-nun özü də pulsuz deyil — hər renderdə dependency array-i əvvəlki ilə müqayisə etmək və nəticəni yaddaşda saxlamaq xərci var. Sadə əməliyyatlar (a + b kimi) üçün bu müqayisə xərci, hesablamanın özündən baha ola bilər.

03

useCallback — funksiyaların yenidən yaradılmasının qarşısını alma

useCallback dəyəri deyil, funksiyanın özünün referansını yaddaşda saxlayır. Riyazi olaraq bu belə ifadə olunur:

Ekvivalentlik
useCallback(fn, deps) === useMemo(() => fn, deps)

Niyə lazımdır: funksiyanı prop kimi React.memo ilə sarılmış child-ə ötürəndə, hər render fərqli funksiya referansı yaradır (function(){} !== function(){}) — bu da React.memo-nun müqayisəsini "sındırır" və child yenə render olunur.

❌ Problem
function Toolbar({ onSave }) {
  const [theme, setTheme] = useState('light');

  // hər renderdə YENİ funksiya yaranır
  const handleClick = () => onSave('draft');

  return <MemoButton onClick={handleClick} />;
}
✅ Həll
function Toolbar({ onSave }) {
  const [theme, setTheme] = useState('light');

  const handleClick = useCallback(() => {
    onSave('draft');
  }, [onSave]); // referans stabildir

  return <MemoButton onClick={handleClick} />;
}
04

React.memo — komponent səviyyəsində optimallaşdırma

React.memo bir HOC (higher-order component) kimi işləyir: komponenti "sarıyır" və hər render öncəsi yeni props-ları əvvəlki render-in props-ları ilə səthi (shallow) müqayisə edir. Əgər hamısı eynidirsə, React komponentin funksiyasını yenidən çağırmır, son render nəticəsini təkrar istifadə edir.

Sintaksis
const ProductCard = React.memo(function ProductCard({ product, onSelect }) {
  return <div onClick={() => onSelect(product.id)}>{product.name}</div>;
});

// xüsusi müqayisə funksiyası ilə:
const ProductCard2 = React.memo(ProductCard, (prev, next) => {
  return prev.product.id === next.product.id;
});

Nə vaxt faydalıdır: tez-tez render olunan valideynin altında yerləşən, render-i nisbətən "baha", props-ları isə az-az dəyişən komponentlərdə.

⚠️

Məhdudiyyətlər:

  • Müqayisə səthidir (shallow) — obyektin içindəki dəyər dəyişsə belə, referans eynidirsə fərq görünmür; referans fərqlidirsə (inline yaradılıbsa) hər dəfə "fərqli" sayılır.
  • children prop-u ötürüləndə demək olar həmişə fərqli referans olur (JSX hər renderdə yeni React element obyekti yaradır) — bu komponentlərdə React.memo çox vaxt işləmir.
  • Müqayisənin özü də pulsuz deyil — çoxlu sayda sadə prop-u olan komponentlərdə bu xərc qazancdan çox ola bilər.
  • React.memo yalnız props-a təsir edir — komponent öz daxilində useState/useContext istifadə edirsə, memo olsa belə yenə render olunacaq.
05

Custom hook yazma prinsipləri

  • Ad mütləq use prefiksi ilə başlamalıdır — React linter yalnız bu halda Hook Qaydalarını yoxlaya bilir.
  • Hook Qaydaları: yalnız komponentin/hook-un "top level"-ində çağırılmalıdır — şərt (if), dövr (for) və ya iç-içə funksiya daxilində yox.
  • Təkrarlanan stateful məntiqi (data fetching, subscription, localStorage sinxronizasiyası və s.) ayrı hook-a çıxarmaq kodu təmiz və test edilə bilən edir.
  • Return API dizaynı: sadə hook-lar üçün array ([value, setValue] — useState kimi) uyğundur; çoxlu dəyər/funksiya qaytaran hook-lar üçün isə object ({ data, loading, error, refetch }) daha oxunaqlıdır, çünki istifadəçiyə adlandırma sərbəstliyi verir.
  • Hook öz daxilində lazım gəldikcə useMemo/useCallback istifadə edərək qaytardığı dəyər və funksiyaların referensial stabilliyini təmin etməlidir — əks halda hook-u çağıran hər komponent lazımsız render-lərlə üzləşəcək.
Qısa nümunə — useDebounce
function useDebounce(value, delay = 300) {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id); // təmizləmə
  }, [value, delay]);

  return debounced;
}

Nəzəriyyədən koda

İndi öyrəndiklərimizi iki real ssenaridə tətbiq edək: böyük bir siyahının axtarış performansını yaxşılaşdırmaq və özümüzün custom hook-larımızı yazmaq.

A

Böyük siyahıda filtrasiya/axtarış performansının optimallaşdırılması

Problem: 10.000 məhsuldan ibarət siyahımız var. Axtarış input-una hər hərf yazıldıqda bütün siyahı yenidən filtr olunur və bütün siyahı elementləri yenidən render olunur — hətta nəticədə heç dəyişməyən elementlər belə.

❌ Optimallaşdırılmamış
function ProductSearch({ products }) {
  const [query, setQuery] = useState('');

  // hər renderdə yenidən hesablanır
  const filtered = products.filter(p =>
    p.name.toLowerCase().includes(query.toLowerCase())
  );

  return (
    <div>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      {filtered.map(p => (
        // hər renderdə YENİ inline funksiya — memo faydasızdır
        <ProductItem key={p.id} product={p}
          onSelect={() => console.log(p.id)} />
      ))}
    </div>
  );
}
✅ Optimallaşdırılmış
const ProductItem = React.memo(function ProductItem({ product, onSelect }) {
  return (
    <div onClick={() => onSelect(product.id)}>{product.name}</div>
  );
});

function ProductSearch({ products }) {
  const [query, setQuery] = useState('');

  // 1) yalnız products və ya query dəyişəndə yenidən hesablanır
  const filtered = useMemo(() =>
    products.filter(p => p.name.toLowerCase().includes(query.toLowerCase())),
    [products, query]
  );

  // 2) referans stabildir — ProductItem-in memo-su işləyir
  const handleSelect = useCallback(id => {
    console.log(id);
  }, []);

  return (
    <div>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      {filtered.map(p => (
        <ProductItem key={p.id} product={p} onSelect={handleSelect} />
      ))}
    </div>
  );
}
✅

Nəticə: axtarış zamanı yalnız siyahının məzmunu (filtered) yenidən hesablanır; artıq siyahıda qalan elementlərin ProductItem komponentləri isə eyni product və eyni (stabil) onSelect referansı aldıqları üçün render-i "atlayır".

B

Öz custom hook-unu yazmaq: useFetch

Data fetching məntiqini təkrarlamamaq üçün, onu loading/error/data vəziyyətlərini idarə edən ayrıca hook-a çıxarırıq. AbortController ilə komponent unmount olanda sorğunu ləğv edirik ki, "unmounted komponentə state yazma" xətası baş verməsin.

hooks/useFetch.js
function useFetch(url) {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    const controller = new AbortController();
    setLoading(true);

    fetch(url, { signal: controller.signal })
      .then(res => res.json())
      .then(json => { setData(json); setError(null); })
      .catch(err => { if (err.name !== 'AbortError') setError(err); })
      .finally(() => setLoading(false));

    return () => controller.abort(); // təmizləmə
  }, [url]);

  return { data, loading, error };
}

// istifadəsi:
function UserProfile({ id }) {
  const { data, loading, error } = useFetch(`/api/users/${id}`);
  if (loading) return <Spinner />;
  if (error) return <Error message={error.message} />;
  return <Profile user={data} />;
}
C

Öz custom hook-unu yazmaq: useLocalStorage

State-i avtomatik olaraq localStorage ilə sinxronlaşdıran hook — useState-in eyni API-sini təqdim edir, sadəcə dəyəri saxlayır.

hooks/useLocalStorage.js
function useLocalStorage(key, initialValue) {
  const [value, setValue] = useState(() => {
    try {
      const saved = window.localStorage.getItem(key);
      return saved !== null ? JSON.parse(saved) : initialValue;
    } catch {
      return initialValue;
    }
  });

  useEffect(() => {
    window.localStorage.setItem(key, JSON.stringify(value));
  }, [key, value]);

  return [value, setValue];
}

// istifadəsi — useState kimi, amma yaddaşda qalır:
const [theme, setTheme] = useLocalStorage('theme', 'light');
Tapşırıq

Axtarış sahəli məhsul siyahısını optimallaşdırın

Aşağıdakı başlanğıc koddan istifadə edərək, dərsdə öyrəndiyimiz üç aləti tətbiq edin.

🎯 Tələblər

  • 100+ elementdən ibarət products massivi və axtarış input-u olan komponenti optimallaşdırın.
  • Filtrasiya məntiqini useMemo ilə əhatə edin, dependency array-i düzgün müəyyən edin (nə artıq, nə əskik).
  • Siyahı elementini (ProductCard) React.memo ilə sarın.
  • Element seçimi üçün handler funksiyasını useCallback ilə stabilləşdirin.
  • React DevTools Profiler ilə əvvəl/sonra render sayını müqayisə edin və nəticəni qeyd edin.
Başlanğıc kod
function ProductSearchPage({ products }) {
  const [query, setQuery] = useState('');
  const [selectedId, setSelectedId] = useState(null);

  // TODO: bunu useMemo ilə əhatə et
  const results = products.filter(p =>
    p.name.toLowerCase().includes(query.toLowerCase())
  );

  return (
    <div>
      <input
        placeholder="Məhsul axtar..."
        value={query}
        onChange={e => setQuery(e.target.value)}
      />
      <ul>
        {results.map(p => (
          // TODO: ProductCard-ı React.memo ilə sar
          // TODO: onSelect-i useCallback ilə stabilləşdir
          <ProductCard
            key={p.id}
            product={p}
            selected={p.id === selectedId}
            onSelect={() => setSelectedId(p.id)}
          />
        ))}
      </ul>
    </div>
  );
}
💡 İpucunu göstər

onSelect={() => setSelectedId(p.id)} sətri sizi çətinliyə sala bilər — burada hər elementin öz id-si funksiyaya "bağlanmalıdır" (closure). Bunun üçün onSelect-i useCallback ilə id qəbul edən bir funksiya kimi yazın (useCallback(id => setSelectedId(id), [])) və ProductCard daxilində onClick={() => onSelect(product.id)} şəklində çağırın — beləcə valideyndəki funksiya referansı hər render üçün stabil qalır.

Ola biləcək xətalar

Tipik səhvlər və bug-lar

Bu optimallaşdırma alətləri düzgün istifadə olunmasa, ya heç bir fayda vermir, ya da yeni bug-lar yaradır. Ən çox rast gəlinən 8 vəziyyət:

01Dependency array-i unutmaq (stale closure)

useMemo/useCallback-ın deps array-ini boş qoymaq və ya natamam yazmaq — nəticədə funksiya köhnə (stale) dəyərlərdən istifadə etməyə davam edir.

✅ ESLint-in react-hooks/exhaustive-deps qaydasını aktiv saxlayın və xəbərdarlıqları görməzdən gəlməyin.
02Deps daxilində hər dəfə yeni referans olan obyekt

Deps array-ində özü hər renderdə yenidən yaradılan inline obyekt ({id} kimi) olması — useMemo "işə düşmür" sayılır, çünki React deps-i "dəyişib" hesab edir.

✅ Deps-ə primitiv dəyərlər (id, string, rəqəm) verin, tam obyekt yox.
03useCallback var, React.memo yoxdur

Funksiya referansı stabildir, amma onu qəbul edən komponent memo ilə sarılmayıb — komponent yenə hər render təkrar işə düşür. useCallback-in faydası sıfıra enir.

✅ useCallback yalnız child React.memo ilə sarılıbsa mənalıdır — ikisini birlikdə düşünün.
04Hər yerə useMemo/useCallback yazmaq

Sadə a + b kimi ucuz əməliyyatlar üçün belə memo istifadə etmək — əlavə yaddaş və müqayisə xərcini artırır, kodu oxunaqsızlaşdırır.

✅ Əvvəlcə profil edin, yalnız real "baha" yerlərdə tətbiq edin.
05children prop-lu komponentə React.memo tətbiq etmək

JSX children hər renderdə yeni React element obyekti olduğu üçün, memo praktiki olaraq heç vaxt "eyni" nəticə vermir.

✅ Composition pattern-dən istifadə edin — dəyişən hissəni yuxarıda saxlayıb, sabit hissəni props kimi ötürün.
06Key kimi massiv index-i istifadə etmək

Sıralama, silmə və əlavə zamanı React-in düzgün diff aparmasına mane olur — həm performans, həm də state qarışması bug-larına (məsələn input-ların "yerinin dəyişməsi") səbəb olur.

✅ Həmişə sabit, unikal id istifadə edin — index yalnız statik, heç vaxt dəyişməyən siyahılarda qəbul edilir.
07useEffect deps-ində memo-lanmamış obyekt

Hər render yeni referans yaradan obyekt/funksiya useEffect-in dependency-sinə verilirsə, effekt hər dəfə (bəzən sonsuz dövrdə) təkrar işə düşür.

✅ Effektə verilən obyekt/funksiyaları da useMemo/useCallback ilə stabilləşdirin.
08Profilsiz, "kor-koranə" optimallaşdırma

Real performans problemi ölçülmədən hər yerə memo əlavə etmək — həm vaxt itkisi, həm də lazımsız mürəkkəblik yaradır (premature optimization).

✅ React DevTools Profiler ilə əvvəlcə "harada, nə qədər" vaxt itdiyini ölçün, sonra düzəldin.
Nələri etsək daha yaxşı olar

Ən yaxşı təcrübələr

Performans optimallaşdırması bir dəfəlik əməliyyat deyil, vərdişdir. Bu prinsiplər həmişə faydalıdır:

📏

Əvvəlcə ölç, sonra optimallaşdır

React DevTools Profiler-in Flamegraph və Ranked chart görünüşü ilə hansı komponentin, niyə render olduğunu real rəqəmlərlə görün.

🏭

Production build üzərində test edin

Development rejimi süni yavaşlığa səbəb olur və real rəqəmlər vermir — ölçmələri həmişə production build-də aparın.

🔦

"Niyə render oldu?" sualına cavab tapın

React DevTools-un "Highlight updates when components render" seçimini aktivləşdirərək lazımsız render-ləri gözlə görün.

⬇️

State-i aşağı səviyyəyə "itələyin"

State colocation — state-i yalnız ona ehtiyacı olan komponentdə saxlayın ki, yuxarı komponentin render-i lazımsız yerə aşağını "sürükləməsin".

🧩

Composition-dan istifadə edin

Dəyişən hissəni yuxarıda saxlayıb sabit hissəni children kimi ötürmək, memoizasiya olmadan da re-render-in "arasından keçməsinə" imkan verir.

🔑

Key-ləri düzgün seçin

Siyahılarda həmişə sabit, unikal id-lərdən istifadə edin — massiv index-indən yox.

📜

Böyük siyahılar üçün virtualizasiyanı düşünün

Minlərlə element varsa, useMemo/React.memo kifayət etməyə bilər — react-window və ya react-virtual kimi kitabxanalar yalnız görünən elementləri render edir.

Erkən optimallaşdırmadan çəkinin

FAQ

Əsas fərq sadədir: useMemo bir dəyəri (hesablamanın nəticəsini) yaddaşda saxlayır, useCallback isə funksiyanın özünü (referansını) yaddaşda saxlayır. Riyazi olaraq: useCallback(fn, deps) === useMemo(() => fn, deps).

Bir-birinə ekvivalenti—useMemo(() => fn, deps)

Çaşdırılan yerlər:

  • useMemo(() => doSomething, []) yazmaq — burada oxlu mötərizə (doSomething()) unudulub, nəticədə hesablamanın nəticəsi deyil, funksiyanın özü qaytarılır. Bu, texniki olaraq işləyir (çünki useCallback kimi davranır), amma niyyəti aydın olmadığı üçün çaşdırıcıdır.
  • "useMemo hər şeyi sürətləndirir" düşüncəsi — əslində yalnız render-lər arasında təkrar hesablamanın qarşısını alır, ilk render-i sürətləndirmir.
  • "useCallback funksiyanın icrasını sürətləndirir" düşüncəsi — əslində icra sürətinə heç bir təsiri yoxdur, sadəcə referansı sabit saxlayır.

Hər useMemo/useCallback çağırışı öz daxilində iki əlavə iş görür: (1) dependency array-in hər elementini əvvəlki render-lə Object.is ilə müqayisə etmək və (2) nəticəni yaddaşda saxlamaq üçün əlavə yer ayırmaq.

Sadə əməliyyatlar üçün (iki ədədi toplamaq, string birləşdirmək və s.) bu müqayisə xərci, əməliyyatın özünün icra xərcindən qat-qat böyük ola bilər — yəni "optimallaşdırma" əslində tətbiqi yavaşladır və yaddaş istifadəsini artırır.

Bundan əlavə, hər yerdə memo istifadəsi kodu şişirdir, oxunaqlılığı azaldır və real problemi gizlədə bilər — developer "memo var, deməli optimaldır" düşüncəsinə düşüb, real profilə heç baxmaya bilər.

Qayda: defolt olaraq memo istifadə etməyin — yalnız Profiler real bir problem göstərəndə tətbiq edin.

Xeyr. Bir sıra hallarda ya faydasızdır, ya da əlavə xərc yaradır:

  • Props demək olar hər render dəyişirsə (animasiya, real-time data) — müqayisə həmişə "fərqli" nəticə verəcək, sadəcə əlavə xərc yaranır.
  • children prop-u olan komponentlərdə — yuxarıda izah olunduğu kimi, JSX children hər renderdə yeni referansdır.
  • Çox "ucuz" (sadə, kiçik) komponentlərdə — render-in özü onsuz da sürətli olduğundan, müqayisə xərci qazancdan çox ola bilər.
  • Props daxilində memo-lanmamış obyekt/array/funksiya varsa — React.memo tək başına, useMemo/useCallback olmadan işləməyəcək.

Nəticə: React.memo bir "alət"dir, "default davranış" deyil — yalnız profil edib real faydasını gördükdən sonra tətbiq edin.
