Error Handling — Xətaların İdarə Edilməsi

Proqram işləyərkən hər şey planlaşdırıldığı kimi getmir: şəbəkə kəsilir, istifadəçi səhv məlumat daxil edir, fayl tapılmır, server cavab vermir. Bu dərsdə həmin anlarda proqramın tamamilə "partlamaması", səhvi tutub ağıllı reaksiya verməsi üçün lazım olan bütün alətləri öyrənəcəyik: try / catch / finally, throw, hazır Error obyektləri və öz xüsusi error tiplərini necə qurmaq.

01 · Giriş

Niyə Error Handling vacibdir?

Sadə bir müqayisə: elektrik sistemində sığorta (fuse) olmasa, kiçik bir qısaqapanma bütün evi yandıra bilər. Error handling da proqram üçün elə bir "sığorta"dır — gözlənilməz bir xəta baş verəndə bütün proqramın çökməsinin qarşısını alır.

JavaScript-də əgər bir xəta tutulmasa (uncaught), brauzerdə həmin skriptin qalan hissəsi dayanır, Node.js-də isə bütün proses çökür. Aşağıdakı nümunəyə bax:

crash-nümunə.js
Console
Proqram başladı
Uncaught TypeError: Cannot read properties of null (reading 'name')
Bu sətir heç vaxt icra olunmayacaq

Gördüyün kimi, xəta baş verən andan sonra kodun qalan hissəsi — hətta xətayla heç bir əlaqəsi olmayan sətirlər belə — işə düşmür. Error handling məhz bunun qarşısını alır: xətanı "tutub" proqrama "bu problem oldu, indi nə edək?" sualına cavab vermək imkanı yaradır.

02 · Əsas mexanizm

Try / Catch / Finally

Bu üç blok error handling-in özəyidir. Hər biri fərqli bir sualın cavabıdır: try — "nəyi sınayırıq?", catch — "xəta olsa nə edirik?", finally — "nə olur-olsun, nəyi mütləq etməliyik?"

Necə işləyir

  • try {} blokuna xəta ehtimalı olan kod yazılır. JavaScript bu kodu sətir-sətir icra edir.
  • Əgər try bloku daxilində heç bir xəta baş verməsə, catch bloku tamamilə atlanır və proqram normal davam edir.
  • Əgər hər hansı sətirdə xəta baş versə, JavaScript try blokunun qalan hissəsini dərhal tərk edir (o sətirdən sonrakı heç nə icra olunmur) və birbaşa catch blokuna keçir.
  • catch (error) {} bloku bir Error obyekti qəbul edir. Bu obyektin .name (xətanın tipi), .message (izahat) və .stack (hansı sətirdə baş verdiyini göstərən "iz") kimi xassələri var.
  • finally {} bloku isə — xəta olsun ya olmasın, hətta try və ya catch daxilində return olsa belə — həmişə icra olunur. Buna görə də bağlantını bağlamaq, loading göstəricisini gizlətmək kimi "təmizlik" işləri üçün ideal yerdir.

03 · Manual xəta yaratmaq

Throw operatoru

throw sənə öz xətanı özün "atmaq" imkanı verir. Bir funksiya daxilində şərt gözlədiyin kimi baş vermirsə, throw ilə icranı dərhal dayandırıb, xətanı ən yaxın catch blokuna (və ya heç biri yoxdursa, çağırış zəncirinin — call stack-in — yuxarısına) ötürə bilərsən.

Nəzəri cəhətdən throw ilə istənilən dəyəri (string, rəqəm, obyekt) atmaq mümkündür, amma yalnız Error obyektlərini (və ya ondan törəyən sinifləri) atmaq ən doğru yanaşmadır — çünki Error obyekti yaradıldığı anda avtomatik olaraq .stack izini özündə saxlayır və bütün alətlər (brauzer, monitorinq sistemləri) məhz bu formatı gözləyir.

04 · Error obyekti

Error obyekti və xüsusi Error növləri

JavaScript-in özündə hazır bir neçə error tipi var — hər biri müəyyən bir problem üçün avtomatik yaranır. Bunlardan əlavə, öz layihən üçün xüsusi (custom) error sinifləri də qura bilərsən.

Daxili (built-in) error növləri

Error
Ümumi, "bazovıy" xəta tipi. Bütün digər error tipləri bundan törəyir.
TypeError
Bir dəyər üzərində, onun tipinə uyğun olmayan əməliyyat edildikdə yaranır. Məsələn, null üzərindən xassə oxumaq.
RangeError
Bir dəyər icazə verilən diapazondan kənara çıxdıqda yaranır. Məsələn, massivə mənfi uzunluq təyin etmək.
ReferenceError
Mövcud olmayan (elan edilməmiş) dəyişənə müraciət edildikdə yaranır.
SyntaxError
Kodun sintaksisi səhvdir. Adətən JSON.parse() kimi runtime-da kod/mətn "oxuyan" funksiyalarda rast gəlinir.
URIError
encodeURI() / decodeURI() düzgün olmayan formatla çağırıldıqda yaranır.

05 · Bug report

Ən çox edilən səhvlər

Error handling yazmaq asandır, amma doğru yazmaq təcrübə tələb edir. Aşağıda yeni başlayanların (və bəzən təcrübəlilərin də) tez-tez düşdüyü səhvlər — "səhv" və "düzgün" kod müqayisəsi ilə.

BUG-01

Boş catch bloku (xətanı udmaq)

Xətanı tutub heç nə etməmək ən təhlükəli vərdişlərdən biridir — proqram "işləyir" kimi görünür, amma arxada nə baş verdiyi tamamilə bilinməz qalır. Bu, gələcəkdə tapılması çox çətin olan gizli bug-lara aparır.

✕ Səhv
✓ Düzgün
BUG-02

Həddindən artıq geniş try bloku

Bütün funksiyanı bir try blokuna doldurmaq, xətanın konkret olaraq hansı sətirdən gəldiyini müəyyən etməyi çətinləşdirir. try blokunu yalnız həqiqətən xəta ehtimalı olan hissə ilə məhdudlaşdır.

✕ Səhv
✓ Düzgün
BUG-03

String (yaxud digər primitiv) atmaq

throw "mətn" texniki olaraq işləyir, amma stack izi olmur, .message / .name kimi standart xassələr yoxdur. Bu, debugging-i və monitorinq alətlərini çətinləşdirir.

✕ Səhv
✓ Düzgün
BUG-04

Asinxron kodda try/catch-i unutmaq

await ilə çağırılan bir sorğu uğursuz olsa, try/catch olmadan bu, "unhandled promise rejection" kimi sükutla (yaxud kontrolsuz şəkildə) proqramı dayandıra bilər.

✓ Düzgün
BUG-05

try/catch callback daxilindəki xətanı tutmur

try/catch yalnız öz sinxron icra bloku daxilində baş verən xətaları tutur. setTimeout, hadisə (event) callback-ləri kimi gələcəkdə icra olunan kodlar xarici try-ın "əhatə dairəsindən" kənardadır.

Bütün error tiplərini eyni cür tutmaq

Validasiya xətası ilə şəbəkə xətasına eyni reaksiyanı vermək istifadəçiyə yanlış mesaj göstərməyə səbəb ola bilər. instanceof ilə error tipini ayırd et.

Nüanslar

JavaScript-in error handling davranışında bir neçə incə, çox vaxt təəccübləndirən detal var. Bunları bilmək debugging zamanı çox vaxt qazandırır.

⚠️
finally, return-u belə üstələyir

Əgər həm try/catch-də, həm də finally-də return yazılsa, finally-dəki qalib gəlir. Bax:

finally-return.js

Nəticə: 2. Bu davranış çox vaxt gözlənilməz bug-lara səbəb olur, ona görə finally daxilində return yazmaqdan çəkin.

🔎
catch dəyişəni yalnız öz bloku daxilində mövcuddur

catch-in (error) parametri blok-səviyyəli (block-scoped) dəyişəndir — catch blokundan kənarda əlçatan deyil. Əgər error-u kənarda istifadə etmək lazımdırsa, onu əvvəlcədən elan olunmuş xarici dəyişənə mənimsətmək lazımdır.

🧩
JavaScript-də "çoxlu catch tipi" yoxdur

Bəzi dillərdə (Java, Python) fərqli error tipləri üçün ayrı-ayrı catch blokları yazmaq mümkündür. JavaScript-də isə bir catch bloku var — fərqli tipləri instanceof ilə özün ayırd etməlisən.

instanceof-ayirma.js
📡
Unhandled promise rejection sükutla itə bilər

Əgər bir Promise rədd edilsə (reject) və heç yerdə .catch() yoxdursa, brauzer konsolunda "Uncaught (in promise)" xəbərdarlığı görünür. Qlobal şəkildə izləmək üçün window.addEventListener('unhandledrejection', ...) istifadə edilə bilər.

🪪
error.stack developer üçündür, istifadəçi üçün yox

Bu xassənin formatı brauzerlər arasında standart deyil və daxili fayl yollarını göstərə bilər. İstifadəçiyə göstərmə — amma Sentry kimi monitorinq sistemlərinə göndərmək üçün çox dəyərlidir.

🎯
Optional catch binding

Əgər error obyektinin özünə ehtiyacın yoxdursa, mötərizəni tamamilə buraxa bilərsən: catch { ... }. Kodu bir az təmizləyir, məntiqi dəyişmir.

🚫
throw hər şeyi qəbul edir, amma hər şeyi atma

Texniki olaraq throw 404; yaxud throw {mesaj: "xəta"}; da işləyir. Amma bu, stack izini itirir və alətlərin gözlədiyi formatı pozur. Həmişə Error (və ya ondan törəyən) obyekt at.

08 · Özünü yoxla

Özünü yoxla

Sualın üzərinə klikləyib cavabı yoxla — əvvəlcə özün cavablandırmağa çalış.

finally bloku, try-də return olsa belə icra olunacaqmı?
Bəli. finally, try/catch-də nə baş verməsindən — hətta return, throw və ya break olsa belə — asılı olmayaraq həmişə icra olunur. Üstəlik, finally daxilində return yazılsa, o, əvvəlki return-u əvəz edir.
throw ilə hansı dəyərləri atmaq olar? Tövsiyə olunan nədir?
Texniki cəhətdən istənilən dəyəri (string, rəqəm, obyekt) atmaq mümkündür. Amma tövsiyə olunan yalnız Error obyekti (və ya ondan törəyən xüsusi sinif) atmaqdır — çünki bu, avtomatik olaraq stack izini və standart .name/.message xassələrini təmin edir.
Niyə boş catch bloku (catch (e) {}) təhlükəlidir?
Çünki xəta sükutla "udulur" — heç bir iz qalmır. Proqram zahirən normal işləyir kimi görünsə də, arxada nəyin səhv getdiyi bilinmir və bu, tapılması çox çətin olan gizli bug-lara səbəb olur.
instanceof niyə xüsusi (custom) error-larla vacibdir?
JavaScript-də bir catch bloku daxilində fərqli error tiplərini ayırd etməyin yeganə yolu instanceof-dur. Bu, məsələn validasiya xətası ilə şəbəkə xətasına fərqli reaksiya vermək üçün lazımdır.
Asinxron (async) funksiyada await edilən sorğunun xətasını necə tuturuq?
await edilən kodu try blokuna alıb, adi sinxron kod kimi catch ilə tuturuq. Alternativ olaraq, funksiyanı çağıran yerdə Promise-ə birbaşa .catch() əlavə etmək də mümkündür.
