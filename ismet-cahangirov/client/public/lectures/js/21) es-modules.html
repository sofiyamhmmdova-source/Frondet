A · 01

ES Modules nədir?

Modul sisteminin JavaScript-ə niyə lazım olduğunu və köhnə üsullardan nə ilə fərqləndiyini anlayaq.

2015-ci ilə qədər JavaScript-də rəsmi modul sistemi yox idi. Böyük layihələrdə kod ya bir-birinin üstünə yazılan <script> teqləri ilə, ya IIFE (dərhal çağırılan funksiya) ilə, ya da Node.js-də CommonJS (require / module.exports) ilə təşkil olunurdu.

ES Modules (ESM) — ECMAScript 2015 standartı ilə gələn rəsmi modul sistemidir. Həm brauzerlərdə, həm də Node.js-də dəstəklənir və bu gün JavaScript ekosisteminin əsas modul formatıdır.

Klassik skriptdən nə ilə fərqlənir?

  • Hər fayl öz scope-una malikdir. Modulun içindəki dəyişənlər avtomatik olaraq window/qlobal obyektə əlavə olunmur.
  • Strict mode avtomatik aktivdir — "use strict" yazmağa ehtiyac yoxdur.
  • Top-level this — modulun içində this undefined-dir (klassik skriptdə isə window-a bərabərdir).
  • Statik strukturdur. import/export yalnız faylın ən yuxarı səviyyəsində yazıla bilər (şərt daxilində yox), buna görə alətlər faylların bir-birinə necə bağlı olduğunu icra olmadan öncə təhlil edə bilir. Elə bu xüsusiyyət tree-shaking-i mümkün edir (9-cu bölmədə).
  • Bir dəfə icra olunur. Modul neçə yerdən import olunsa da, onun kodu yalnız bir dəfə işə düşür, nəticə keşlənir.
A · 02

Əsas sintaksis: export və import

Bir faylın kodu necə "ixrac" edilir və başqa fayldan necə "idxal" olunur.

mathUtils.js
export const PI = 3.14159;

export function add(a, b) {
  return a + b;
}

export function subtract(a, b) {
  return a - b;
}
app.js
import { PI, add, subtract } from './mathUtils.js';

console.log(add(2, 3)); // 5

İstəsən, export-ları funksiyaların yanında yazmaq əvəzinə, faylın sonunda tək bir yerdə toplaya bilərsən:

mathUtils.js — alternativ yazılış
const PI = 3.14159;
function add(a, b) { return a + b; }
function subtract(a, b) { return a - b; }

export { PI, add, subtract };
Nüans: import zamanı ad dəyişmək istəsən, as açar sözündən istifadə et: import { add as toplama } from './mathUtils.js'. Eyni şəkildə export edərkən də export { add as cəm } yaza bilərsən.
A · 03

Named export vs Default export

İkisi arasındakı fərqi bilməmək ən çox rast gəlinən qarışıqlıqlardan biridir.

NamedDefault
SayıBir modulda istənilən qədər ola bilərBir modulda yalnız bir dənə ola bilər
Import zamanı adMötərizə { } daxilində, orijinal adla eyni olmalıdır (və ya as ilə çevrilməlidir)Mötərizə lazım deyil, istənilən adı özün seçə bilərsən
Tipik istifadəUtil funksiyalar, sabitlər, çoxlu köməkçi ifadələrBir faylın "əsas" ixracı — məs. tək bir komponent və ya class
RefaktorinqIDE adı avtomatik izləyir, səhv adı asan tapılırAd sərbəst olduğu üçün eyni şeyin fərqli fayllarda fərqli adlanma riski var
Named export 
export function formatDate(d) {...}
// başqa fayldan:
import { formatDate } from './date.js';
Default export 
export default function Button(props) {...}
// başqa fayldan, istənilən adla:
import Duyme from './Button.js';

Nə vaxt hansını seçmək lazımdır?

Bir modulda hər ikisini eyni anda istifadə etmək də olar:

import — həm default, həm named
import Calculator, { add, subtract } from './Calculator.js';

Əksər müasir layihələrdə (məsələn Airbnb JS Style Guide) named export-a üstünlük vermək tövsiyə olunur: ad sərbəstliyi olmadığı üçün import olunan adlar bütün layihə boyu eyni qalır, bu da axtarışı və avtomatik refaktorinqi asanlaşdırır. Default export daha çox "bu faylın tək bir əsas nəticəsi var" mənasını daşıyan hallarda (məs. bir React komponenti) məntiqlidir — amma bunun da öz xətaları var (7-ci bölmədə).

A · 04

Modul arxitekturası

Faylları necə təşkil etmək, "barrel" fayllar və dairəvi asılılıq problemi.

Tipik qovluq strukturu

qovluq ağacı
src/
├── components/
│   ├── Button.js
│   ├── Modal.js
│   └── index.js        // "barrel" fayl
├── utils/
│   ├── formatDate.js
│   └── validate.js
└── app.js

Barrel fayl (index.js)

Barrel fayl bir qovluqdakı bütün modulları tək yerdən yenidən ixrac edir ki, import yolları qısa olsun:

components/index.js
export { default as Button } from './Button.js';
export { default as Modal } from './Modal.js';

Nəticədə başqa fayldan import { Button, Modal } from './components' yazmaq kifayətdir. Rahatdır, amma qiyməti var:

  • Bəzi bundler-lər barrel faylın bütün tərkibini yükləyə bilir, hətta yalnız bir hissəsi lazım olsa belə — bu tree-shaking-i çətinləşdirir.
  • Böyük layihələrdə barrel fayllar dairəvi asılılıq (circular dependency) riskini artırır, çünki bir-birinə bağlı çoxlu fayl eyni giriş nöqtəsindən keçir.
⚠ Diqqət — Dairəvi asılılıq

a.js və b.js bir-birini import edir

Modullar yuxarıdan aşağı, bir dəfə icra olunur. Əgər a.js icra olunarkən b.js-i çağırır, o da öz növbəsində hələ tam icra olunmamış a.js-dən bir dəyər istəyirsə, həmin dəyər həmin an undefined ola bilər.

a.js
import { b } from './b.js';
export const a = 'A';
console.log(b); // çox güman ki undefined

Həll yolu: arxitekturanı qatlara (layers) böl — ortaq lazım olan dəyəri ayrıca, üçüncü bir modula çıxar ki, hər iki fayl ondan asılı olsun, bir-birindən yox.

A · 05

Dinamik import()

Modulu yalnız lazım olduğu anda, işə düşərkən yükləmək — code-splitting üçün əsas mexanizm.

İndiyə qədər gördüyümüz import ifadəsi statikdir — faylın ən yuxarısında yazılır və modul yüklənən kimi işə düşür. import() funksiyası isə fərqli işləyir: istənilən yerdə çağırıla bilər və bir Promise qaytarır.

lazy-load nümunəsi
button.addEventListener('click', async () => {
  const module = await import('./heavyChart.js');
  module.renderChart();
});

Bu üsul code-splitting adlanır: istifadəçi düyməni basmayana qədər heavyChart.js ümumiyyətlə brauzerə yüklənmir. Nəticədə ilkin səhifə yükləmə vaxtı qısalır. Bundler-lər (Vite, Webpack) import() gördükdə həmin kodu avtomatik ayrı bir fayla ("chunk") bölür.

Nüans: Modulun ən yuxarı səviyyəsində await import(...) yazmaq da mümkündür — buna top-level await deyilir, amma bu, həmin modulu import edən bütün digər modulların yüklənməsini gecikdirə bilər, ona görə diqqətli istifadə et.
A · 06

Brauzer və Node.js fərqləri

Eyni sintaksis, iki fərqli mühit — hər birinin öz qaydaları var.

Brauzerdə

  • HTML-də <script type="module"> yazılmalıdır, əks halda import/export tanınmır.
  • Modul skriptləri avtomatik defer olunur — HTML tam təhlil olunandan sonra icra olunur.
  • Nisbi yol mütləq faylın tam uzantısı ilə yazılmalıdır: ./utils.js, təkcə ./utils yox.
  • Modulları birbaşa file:// protokolu ilə (fayl ikonuna iki dəfə klikləməklə) açmaq CORS xətası verir — lokal server lazımdır (məs. VS Code-da "Live Server" əlavəsi).

Node.js-də

  • Fayl uzantısı .mjs olsun, və ya package.json faylına "type": "module" əlavə et.
  • CommonJS (require/module.exports) və ESM (import/export) qarışdırılanda gözlənilməz problemlər yarana bilər — bir layihə daxilində, mümkünsə, yalnız birini seç.
  • ESM-də relyativ importlarda da uzantı tələb olunur — bu, CommonJS-dən (require('./utils') uzantısız işləyir) gələnlər üçün ən çox rast gəlinən sürprizlərdən biridir.
⚠ Diqqət — bare specifier

npm paketini brauzerdə birbaşa import etmək

Bundler və ya Node.js-də import react from 'react' normal işləyir, çünki node_modules qovluğunda axtarış aparılır. Sadə bir <script type="module">-də (bundler olmadan) bu, brauzerdə "Failed to resolve module specifier" xətası verir — brauzer /, ./ və ya ../ ilə başlamayan yolu haradan tapacağını bilmir. Həll: tam CDN URL-i yaz və ya bir <script type="importmap"> təyin et.

A · 07

Ən çox rast gəlinən xətalar

Bu bölmədəki hər kart real konsol xətasını və düzəlişini göstərir.

⚠ Bug 1

"Cannot use import statement outside a module"

Ən klassik xəta. Səbəb: HTML-də skript teqinə type="module" yazılmayıb.

❌ Səhv
<script src="app.js"></script>
✅ Düzgün
<script type="module" src="app.js"></script>
⚠ Bug 2

CORS xətası — "has been blocked by CORS policy"

Səbəb: HTML faylı birbaşa file:// ilə açılıb. Modul faylları təhlükəsizlik qaydalarına görə HTTP protokolu üzərindən yüklənməlidir.

Həll: layihəni lokal bir serverdən (VS Code Live Server, npx serve, python -m http.server və s.) aç.

⚠ Bug 3

Fayl yolunda uzantını unutmaq

❌ Səhv (brauzerdə işləmir)
import { add } from './mathUtils';
✅ Düzgün
import { add } from './mathUtils.js';
⚠ Bug 4

Default export-u mötərizə ilə import etmək

❌ Səhv
// Calculator default ixrac olunub, amma
import { Calculator } from './Calculator.js';
// nəticə: undefined
✅ Düzgün
import Calculator from './Calculator.js';

Əksinə də olur: named export-u mötərizəsiz import etməyə çalışmaq — bu isə birbaşa "SyntaxError" ilə nəticələnir.

⚠ Bug 5

Named export adını səhv yazmaq

Import edilən ad mənbə fayldakı adla hərfbəhərf üst-üstə düşməlidir. Kiçik bir yazı səhvi (formatdate əvəzinə formatDate) bəzi bundler quraşdırmalarında sakit şəkildə undefined qaytara bilər, əsl ES modullarında isə birbaşa xəta verir — hər iki halda ilk yoxlanmalı yer import adının orfoqrafiyasıdır.

⚠ Bug 6

"Live binding" ilə bağlı çaşqınlıq

İdxal olunan ad öz modulunda oxu-yalnız (read-only) bağlamadır — bu, dəyərin köçürülməsi deyil, canlı bir istinaddır. Mənbə fayl dəyəri sonradan dəyişsə, import edən tərəfdə də avtomatik yenilənir. Amma import edən tərəf həmin adı özü yenidən mənimsətməyə çalışsa, JavaScript xəta verəcək.

counter.js
export let count = 0;
export function increment() { count++; }
❌ Xəta verir
import { count } from './counter.js';
count = 5; // import bağlaması oxu-yalnızdır
✅ Düzgün üsul
import { count, increment } from './counter.js';
increment(); // count indi mənbədə də yenilənib
⚠ Bug 7

Gözlənilən tree-shaking baş vermir

Bəzən istifadə olunmayan kod bundle-dan çıxarılmır. Ən çox səbəb: modulun daxilində "yan təsirli" (side-effect) kod olması — məsələn faylın ən yuxarısında birbaşa işə düşən bir console.log() və ya qlobal state dəyişikliyi. Bundler bu cür kodu təhlükəsiz şəkildə silə bilmədiyi üçün ehtiyat edib bütün modulu saxlayır. 9-cu bölmədə bunun həllini görəcəyik.

A · 08

Ən yaxşı təcrübələr

Böyüyən layihələrdə modul kodu təmiz saxlamaq üçün qısa qaydalar.

1. Əksər hallarda named export seç. İstisna olaraq, bir faylın həqiqətən tək bir "əsas" ixracı varsa (məs. tək bir komponent), default məntiqli ola bilər.
2. Bir fayl = bir məsuliyyət. Hər modul aydın, dar bir işi görsün; bu həm oxunaqlılığı, həm tree-shaking-i yaxşılaşdırır.
3. Barrel fayllardan ehtiyatla istifadə et. Kiçik, sabit qovluqlarda rahatdır, amma böyük, tez-tez dəyişən modullarda performans və dairəvi asılılıq riskini artıra bilər.
4. Importları qruplaşdır. Əvvəlcə xarici paketlər (react, lodash), sonra daxili modullar (./utils) — kodu tez oxumaq üçün faydalıdır.
5. Nisbi yollarda uzantını həmişə yaz. Brauzer və Node ESM-də bu, seçim deyil, tələbdir.
6. Arxitekturanı qatlara böl. A → B → C istiqamətində axan aydın bir asılılıq zənciri qur ki, dairəvi importlara ehtiyac qalmasın.
A · 09

Performans: Tree-Shaking necə işləyir?

ES Modules-in statik strukturu bundler-lərə istifadə olunmayan kodu silmək imkanı verir.

CommonJS-də require() istənilən yerdə, şərt daxilində, hətta dəyişən adla çağırıla bilər — bu, tam dinamikdir. Bundler icra olmadan əvvəl hansı export-un istifadə olunacağını əminliklə bilə bilmir, ona görə CommonJS kodunu etibarlı şəkildə "silkələyib" (shake) təmizləmək çətindir.

ES Modules isə əksinədir: import/export yalnız faylın ən yuxarısında, sabit adlarla yazıla bilər. Bu, bundler-ə (Webpack, Rollup, esbuild, Vite) icra olmadan əvvəl bütün asılılıq qrafikini dəqiq təhlil etmək imkanı verir — istifadə olunmayan export-lar isə son bundle-dan çıxarılır.

package.json — side-effect siqnalı
{
  "name": "my-lib",
  "sideEffects": false
}

"sideEffects": false bundler-ə "bu paketdəki modulları import etmək özlüyündə heç bir qlobal təsir yaratmır, istifadə olunmayan hissələri arxayın sil" siqnalını verir. Əgər bəzi fayllarda həqiqətən yan təsir varsa (məs. bir CSS faylını qlobal tətbiq edən import), o faylları massiv şəklində istisna kimi göstərmək lazımdır.

A · 10

Özünü yoxla

Cavabı görmək üçün sualın üzərinə klikləyin.

Bir modulda neçə default export ola bilər?
Yalnız bir dənə. Named export isə istənilən sayda ola bilər.
Brauzerdə import işləməsi üçün skript teqinə nə yazılmalıdır?
type="module" — yəni <script type="module" src="app.js"></script>.
Niyə CommonJS-i tam etibarlı şəkildə tree-shake etmək çətindir?
require() dinamik olduğu üçün (şərt daxilində, dəyişən adla çağırıla bilər) bundler icra olmadan əvvəl hansı kodun lazım olduğunu dəqiq bilə bilmir.
İdxal olunan (import edilən) adı birbaşa yenidən mənimsətmək (=) olur mu?
Xeyr. İmport bağlaması oxu-yalnızdır (read-only, "live binding"). Dəyəri dəyişmək üçün mənbə moduldakı bir funksiyadan (məs. increment()) istifadə olunmalıdır.
Node.js-də bir .js faylını ESM kimi işə salmağın iki yolu nədir?
1) faylın uzantısını .mjs etmək, 2) package.json-a "type": "module" əlavə etmək.
